# Verification

Claim nothing you have not just proven. A completion claim is a statement about evidence, and evidence from a previous run or a different tree is not evidence about this one.

## Overview

Before any success claim, run the check that proves it, against the current tree, and read the output. The claim is only as good as the evidence from the tree in front of you: a passing run on an earlier revision, or in another checkout, says nothing about the change you just made. Scope the verification to the change at hand rather than re-running everything; the goal is proof for this claim, not a full-suite ceremony. State the command, its observed result, and anything you could not run.

## When to Use

- You are about to say work is complete, fixed, or passing.
- You are about to commit, open a PR, or report a task done.
- You feel satisfied with a change but have not run its check on this tree.
- A delegated agent reports success and you are about to relay it.
- A check could not be run and you are tempted to imply it passed.

## Process

### 1. Name the claim and its proof

State the exact claim you are about to make, then the check that would prove it for the change at hand: a test command, a build, a linter, a repro. The proof is specific to the claim, so a linter does not prove a build and a nearby passing test does not prove the changed path. If no check can prove the claim, say so: the missing check is itself the finding.

### 2. Run it fresh on the current tree

Run the full command now, in the working tree you are claiming about, after your change. A prior run, another branch, a cached result, or "it passed earlier" is not evidence about this tree. Run the whole command **that proves the claim**, not a partial subset of it.

### 3. Read the output, not just the vibe

Check the exit code, read the failures, and count the results. Absence of obvious red is not a pass; confirm the output actually says what a pass looks like for this command.

### 4. Match the evidence to the claim

Decide whether the output proves the claim. If it does not, state the actual status with the evidence: what failed, or what remains unproven. Never round a partial result up to a pass.

### 5. Claim with evidence, or report the gap

Make the claim together with the command and its observed result. If a check could not be run, report that plainly and say why, so the gap is visible rather than implied away.

## Gates

- **No completion claim without fresh evidence from the current tree.** A prior run or another checkout does not count.
- **Every claim names its check and its observed result.** The command and the output travel with the claim.
- **Scoped to the change at hand.** Prove the specific claim; do not blanket-run everything, and do not let an unrelated passing check stand in for the missing one.
- **Unrun checks are reported as unrun.** They are never implied to pass.
- **Delegated success is verified independently.** An agent's report is a lead, not evidence, until you check the change yourself.

## Anti-patterns

- Claiming a pass from a prior run, another branch, a cache, or memory.
- "Should", "probably", or "seems to" in place of a run.
- Expressing satisfaction, or saying "done", before the check.
- Treating a partial or unrelated check as proof of the whole claim.
- Relaying an agent's success report without verifying it.
- Burying or omitting a check that could not be run.
- Turning verification into a full-suite re-run unrelated to the claim.
