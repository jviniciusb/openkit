# Interview

Turn a rough idea into a shared understanding before anything gets built. The interview maps the design as a tree, works it in rounds, and keeps implementation behind an approval gate.

## Overview

An interview is a relentless but friendly conversation. You map every open decision as a **design tree**: each decision branches into the decisions that hang off it. You ask the questions whose prerequisites are already settled, look facts up yourself, and attach a recommended answer to every question. The interview ends when nothing is left silently assumed and the user confirms you share an understanding.

## When to Use

- The user wants to align on design or requirements before implementation.
- The user asks to stress-test a plan, decision, or idea, or says "grill me".
- Work is about to start on a feature, component, or project whose intent is still fuzzy.

## Process

### 1. Size the work

Classify the work and say the size in plain words. The user can override it.

| Size | The full description | Then |
|------|----------------------|------|
| Spike | a throwaway build | learn from it and return to the interview |
| Bounded | the design, in chat | build it after approval |
| Architectural | a written spec | get the spec approved, then build |

A **spike** is a quick throwaway build, often the cheapest way to learn what the user wants or whether something works. Keep it labeled throwaway, and bring what it taught you back into the conversation. If the work grows mid-task, stop, say so, and step up a size.

### 2. Map the design tree

List the decisions. Every decision branches into the decisions that hang off it. The **frontier** is every decision whose prerequisites are already settled: the questions you can ask now without guessing at answers you have not heard.

### 3. Work the frontier in rounds

Ask the whole frontier together in one round. Number each question and give your recommended answer. Then wait for the user's answers before the next round. Their answers reshape the tree: settled decisions push the frontier outward and unblock the questions that depended on them. A question whose answer depends on another question still open this round belongs to a later round.

Format a round like so:

```
Q1 - <question title>: <question body, possibly with choices>

> <your recommended answer>

---

Q2 - <question title>: <question body>

> <your recommended answer>
```

### 4. Look facts up yourself

Finding facts is your job, never the user's. When a frontier question needs a fact from the environment (files, code, tools, or the web), look it up instead of asking. Do not block the round on it: a running lookup is an unsettled prerequisite, so only the questions downstream of it wait. Ask the rest of the frontier now. The decisions are the user's: put each to them and wait.

### 5. Confirm shared understanding

The interview is done when the frontier is empty and every branch has been visited. Play back the settled decisions in the user's words, mark anything you are guessing as your guess, and ask what is wrong or missing. Only what the user confirms is theirs.

## Gates

- **No implementation before approval.** Writing product code, scaffolding, installing dependencies, and creating projects wait until the user approves the design. Reading and exploring are always fine.
- **A spike may be built** once the user approves it, and it stays labeled throwaway. Keeping what it produced is a new request that comes back through this gate.
- **Architectural work has a written spec.** The spec is the contract; the user approves it before implementation starts.
- **Act only after the frontier is empty** and the user confirms you share an understanding.

## Anti-patterns

- Asking the user for a fact you can look up yourself.
- Asking a question whose prerequisites are still open; it belongs to a later round.
- Sending the whole tree as one questionnaire instead of working the frontier in rounds.
- Starting to build before the design is approved.
- Treating a spike's output as the product.
- Filling gaps silently instead of surfacing them as questions with a recommended answer.
