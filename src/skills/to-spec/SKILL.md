# To Spec

Synthesize the current conversation into a written spec. Do not interview the user: write down the decisions that were already made, invent nothing, and leave undecided items as open questions.

## Overview

A spec produced from a conversation is a distillation, not a new round of design. Everything it states must already have been decided in the conversation or the codebase. The value is in preserving those decisions exactly and surfacing what is still open, so the work can proceed without re-litigating what was settled. If a requirement was never discussed, it does not go in the spec: it becomes an open question.

## When to Use

- The user explicitly invokes this to turn the conversation into a spec.
- A discussion has settled enough decisions that they should be captured in writing.
- The user asks to write up what has been decided so far, or to produce a spec from this conversation.
- The decisions need a durable artifact before implementation starts.

## Process

### 1. Gather the decisions

Read the conversation and the codebase for what has already been decided: chosen approaches, constraints, interfaces, non-goals, and the reasons behind them. Do not ask the user to restate them, and do not add requirements that were never discussed. If the user did not name a location for the spec, ask for one before writing.

### 2. Preserve the exact decisions

Keep each decision as it was made. Use the same names, choices, and constraints the conversation settled on. Do not reword a decision into a different or stronger commitment, and do not resolve anything the conversation left undecided.

### 3. Write the sections

Produce the spec with these sections, in order:

- **Summary**: what this spec is for, in a few sentences.
- **Intent and context**: why the work is being done and the situation it addresses.
- **Requirements**: what must be true when the work is done, each traced to a decision already made.
- **Non-goals**: what is deliberately out of scope.
- **Open questions**: what remains undecided, with what is needed to settle each.

Every requirement traces to a decision in the conversation. Anything unresolved belongs under open questions, not filled in with a plausible answer.

### 4. Write it where the user said

Write the spec to the exact path the user names. Do not choose a different location, and do not scatter the content across several files.

### 5. Report where it landed

Tell the user the path the spec was written to, and call out any open questions that still need a decision.

## Gates

- **Synthesis, not interview.** No new requirements are gathered; the spec captures only what the conversation already decided.
- **Exact decisions preserved.** Names, choices, and constraints stay as decided, not reworded into new commitments.
- **Nothing invented.** Every requirement traces to a decision made in the conversation or the codebase.
- **Unresolved stays open.** Undecided items are listed under open questions, never filled in.
- **Written where the user said.** The spec lands at the path the user named.
- **Self-contained.** No external references in the spec.

## Anti-patterns

- Interviewing the user for requirements the conversation did not already establish.
- Inventing requirements or acceptance criteria that were never decided.
- Rewording a settled decision into a different commitment.
- Writing to a location the user did not name.
- Filling an undecided item with a plausible answer instead of listing it as an open question.
- Restating the conversation as a transcript instead of distilling the decisions.
