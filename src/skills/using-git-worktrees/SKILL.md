# Using Git Worktrees

Set up or verify an isolated workspace before feature work. Detect isolation first, prefer the harness's native worktree tool, and fall back to `git worktree` only when no native tool exists.

## Overview

Isolation keeps feature work off the branch you are currently on. The core principle is a fixed order: detect existing isolation first, then use the harness's native worktree tool, then fall back to manual git only when no native tool exists. Never create a worktree you do not need, and never hand-roll one the harness already manages, because that creates state it cannot see or clean up.

## When to Use

- Starting feature work that needs isolation from the current workspace.
- Before executing an implementation plan, so the plan runs on its own branch.
- The current checkout sits on a branch you must not disturb.

Do not create a worktree when:

- The workspace is already isolated (a linked worktree).
- You are inside a git submodule.

## Process

### 1. Detect existing isolation

Before creating anything, check whether you are already isolated. A linked worktree has a git directory that differs from the common git directory:

```bash
git rev-parse --git-dir
git rev-parse --git-common-dir
```

Different paths mean you are already in a linked worktree. Report the path and branch, then go to the baseline step. Do not create another worktree.

Guard against the submodule false positive: the same difference is also true inside a submodule. Check:

```bash
git rev-parse --show-superproject-working-tree
```

A non-empty result means a submodule, not a worktree. Treat it as a normal repo, and never create a worktree inside it.

### 2. Prefer the native worktree tool

If you are not isolated, use the harness's own worktree tool. In OpenCode that is `worktree_create` with a name; `worktree_list` shows existing worktrees, and `worktree_remove` removes one when it is no longer needed. When the new worktree becomes the working directory, move the session there with `session_move` so the rest of the work happens inside it.

Native tools own placement, branch creation, and cleanup. Running `git worktree add` alongside a native tool creates state the harness cannot see or manage. If the user has not already asked for isolation, ask before creating one.

### 3. Fall back to git worktree

Only when no native worktree tool exists, create the worktree manually. Choose the directory in this order: an explicit preference from your instructions, then an existing project-local `.worktrees/` (or `worktrees/`), then the `.worktrees/` default at the project root.

Before creating a project-local directory, verify it is gitignored:

```bash
git check-ignore -q .worktrees
```

An unignored worktree directory commits the entire worktree into the repository. If it is not ignored, add it to `.gitignore` and commit that change first. Then create the worktree:

```bash
git worktree add "$path" -b "$branch"
```

### 4. Run a clean baseline

In the isolated workspace, install dependencies if the project needs them, then run the test suite before making changes. A clean baseline makes every later failure attributable to your change. If the baseline is red, report the failures and ask whether to proceed or investigate before starting.

## Gates

- **Detect isolation before creating anything.** A linked worktree is already isolated; do not create a second one.
- **Submodules are not worktrees.** A non-empty `git rev-parse --show-superproject-working-tree` means a submodule. Never create a worktree inside one.
- **Native tool first.** Use `worktree_create` / `worktree_list` / `worktree_remove`; fall back to `git worktree add` only when no native tool exists.
- **Gitignored directory before the manual fallback.** Verify with `git check-ignore`; an unignored worktree directory commits the whole tree.
- **Clean baseline before starting.** Run the tests and report the result before feature work begins.
- **The worktree becomes the working directory.** Move the session with `session_move` so work happens inside the isolated tree.

## Anti-patterns

- Creating a worktree without checking whether one already exists.
- Hand-rolling `git worktree add` when the harness has a native worktree tool.
- Creating a worktree inside a submodule.
- Creating a project-local worktree directory that is not gitignored.
- Starting feature work on a red baseline.
- Leaving the session in the original checkout after creating a worktree elsewhere.
