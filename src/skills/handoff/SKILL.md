# Handoff

Compact the current conversation into one portable document a fresh session can resume from with no other memory. Keep it concise and self-contained, and write it where the user can reach it.

## Overview

A handoff is a snapshot of work in progress, written for a reader who was not here. It carries the essentials another session needs: the current state, the decisions made and why, the threads still open, the immediate next action, and pointers to the files, paths, and commands involved. It is not a transcript and not a restatement of artifacts that already exist on disk. Reference those by path instead.

## When to Use

- The user wants to hand the current work off to another session, or to a later one.
- The user asks to summarize where things stand, or to capture state before pausing.
- Context is about to run out and the work needs to survive into a fresh conversation.

## Process

### 1. Choose where it goes

Write the document to a portable location the user can reach. A path the user names always wins. Otherwise use a gitignored or temporary location — the OS temp directory, or a path you have confirmed is gitignored (`git check-ignore <path>`). Never write it to the repository root, into a dev-only internal directory such as `skill-sources/`, or to any tracked path: the document can carry sensitive context and must not be committed by accident.

### 2. Capture the essentials

Record only what a fresh session needs to continue:

- **Current state**: what is done, what is in progress, and where the work stands.
- **Decisions made and why**: each choice that constrains the work, with its reason.
- **Open threads and questions**: what is unresolved, and what is still being decided.
- **Immediate next action**: the single thing to do next.
- **Pointers**: the files, paths, commands, and artifacts involved.

### 3. Reference, do not duplicate

Name existing artifacts by path or URL: specs, plans, commits, diffs, issues. Do not copy their content into the handoff.

### 4. Redact sensitive information

Remove API keys, passwords, tokens, and personally identifiable information before writing.

### 5. Write it and report the path

Save the document, then tell the user exactly where it was written so they can pass it to the next session.

## Gates

- **Portable location.** The document lands at a path the user can reach — a user-named path, or failing that a gitignored or temporary location — never the repository root, `skill-sources/`, or any tracked path.
- **Self-contained.** A fresh session with no memory of this conversation can resume from the document alone.
- **Essentials present.** State, decisions and why, open threads, the immediate next action, and pointers are all captured.
- **Secrets redacted.** No keys, passwords, tokens, or personally identifiable information.
- **Concise.** It reads as a snapshot, not a transcript.

## Anti-patterns

- Writing the handoff to the repository root, into `skill-sources/` or another dev-only internal directory, or to any tracked path.
- Dumping a transcript instead of distilling the essentials.
- Restating artifacts that already exist instead of pointing to them by path.
- Omitting the decisions and the reasons behind them.
- Leaving the next action vague or implicit.
- Including secrets or personally identifiable information.
