# Prototype

A prototype is throwaway code that answers a question. The question decides the shape, and the artifact is disposable by design.

## Overview

A prototype exists to resolve a design uncertainty that reasoning alone cannot settle. Build the smallest artifact that answers ONE question, keep it out of the real code path, and let the answer inform the real implementation. The prototype is a probe, not a deliverable: once it has done its job it is deleted or clearly marked as throwaway. Prefer the cheapest thing that resolves the uncertainty; a throwaway script or a single file beats a scaffolded app.

## When to Use

- A design question needs runnable code to answer before you commit to an approach.
- You are unsure whether a state model or piece of logic feels right in practice.
- You need to see what an interface could look like before choosing one.
- The cost of building to find out is lower than the cost of reasoning it out.
- You want to compare approaches that are hard to judge on paper.

## Process

### 1. Name the one question

State the single design question the prototype answers. If it cannot be phrased as a question with an observable answer, it is not ready to prototype. One prototype answers one question; a second question is a second prototype.

### 2. Pick the cheapest shape

Choose the smallest artifact that answers the question. A logic or state question wants a tiny runnable harness that pushes the model through the awkward cases; a look-and-feel question wants a few quick variations of the thing. A throwaway script or a single file is usually enough. Build only what the question needs: no tests, no error handling beyond what makes it runnable, no abstractions.

### 3. Keep it out of the real code path

Place the prototype where its context is obvious but a casual reader sees it is disposable, and keep it off the production path. Never let the prototype's code, files, or wiring become the real implementation. For an interface, follow the project's existing conventions rather than inventing new structure; for state, keep it in memory unless the question itself is about persistence.

### 4. Make it trivial to run

One command, or one file to open, with no setup thinking required. A prototype that takes effort to start will not get used.

### 5. Surface what changed

After every action, render or print the full relevant state so the answer is visible rather than inferred. The prototype's job is to make the uncertainty observable.

### 6. Report what you learned

State the verdict and the question it settled. Fold the validated decision into the real code, and report the answer plainly, including what the prototype ruled out.

### 7. Delete it or mark it throwaway

Once the answer is captured, delete the prototype, or leave it clearly named and marked as throwaway. The real code path keeps only the validated decision, never the probe.

## Gates

- **One question per prototype.** A prototype that answers several questions answers none clearly.
- **Throwaway from the start, and marked as such.** A reader can tell it is a prototype, not production.
- **Out of the real code path.** No prototype code, file, or wiring becomes the implementation.
- **The cheapest thing that resolves the uncertainty.** Prefer the smallest artifact over a scaffolded app.
- **The learning is reported.** The verdict and the question it settled are stated, not left implicit.
- **Deleted or clearly marked throwaway when done.** The real code keeps only the validated decision.

## Anti-patterns

- Building a prototype that answers no question, or several at once.
- Letting prototype code drift into the production path.
- Polishing: adding tests, abstractions, or error handling the question does not need.
- Choosing an elaborate scaffold when a single file would answer it.
- Leaving an unmarked, half-built prototype in the tree.
- Capturing the answer only in the prototype instead of reporting it.
